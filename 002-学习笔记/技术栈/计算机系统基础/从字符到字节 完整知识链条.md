先记住最重要的一条：

```text
读取：外部字节 → 按指定编码解码 → Java String
写出：Java String → 按指定编码编码 → 外部字节
```

**编码不会自动协商。**读取方必须知道字节原本采用什么编码，才能正确解码；写出方也要明确目标编码。否则就可能出现乱码。

## 1. 字符、编号、编码和字形

这几个概念要分开：

- **字符**：文本中的抽象单位，例如字母 `A` 或汉字“中”。

- **码点**：字符在某套编码标准中的数字编号，例如 Unicode 的 `A` 是 `U+0041`。

- **编码方式**：规定编号怎样转换成字节，例如 UTF-8。

- **字形**：字体最终画出来的形状。一个用户看到的符号也可能由多个码点组合而成。

可以把 Unicode 的主要过程记成：

```text
抽象字符 → Unicode 码点 → UTF 编码 → 字节
```

日常交流中，“字符集”“编码”“字符编码”经常被混着说。Java API 中的 `Charset` 也把 UTF-8、UTF-16 这样的编码称作 charset；严格讨论时，最好说明自己说的是**字符范围/码点**还是**字节转换规则**。

## 2. ASCII：编号与字节值很接近

ASCII 包含英文字母、数字、标点和控制字符，共 128 个代码，用 7 位表示。常见计算机把它放进一个 8 位字节，最高位为 0，所以字符的 ASCII 编号通常就等于它存储的那个字节值。

例如：

```text
A：ASCII 编号 0x41 → 字节 0x41
```

这并不意味着字符天然就是某个字节，而是 ASCII 标准规定了这种映射。Unicode 的前 128 个码点与 ASCII 保持相同编号；UTF-8 对这部分也保留相同的字节值。[RFC 20：ASCII 格式](https://www.rfc-editor.org/info/rfc20/) [Unicode：UTF-8/16/32 FAQ](https://www.unicode.org/faq/utf_bom.html)

## 3. 中文旧编码：区位码、国标码和机内码

中文字符数量远超一个字节能表示的范围。GB 2312 把常用汉字和符号安排在一个 `94 × 94` 的表格中，于是可以用“区”和“位”定位。GB 2312-1980 于 1980 年发布，1981 年实施。[国家标准平台：GB/T 2312-1980](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=5664A728BD9D523DE3B99BC37AC7A2CC)

以“啊”为例，用常见教材模型表示：

```text
区位：16 区 1 位
国标码：30 21
常见机内码/外部字节：B0 A1
```

解码时，可以把过程理解成反向查表：从字节 `B0 A1` 去掉最高位得到 `30 21`，每个字节再减去 `0x20` 得到区位 `10 01`，也就是第 16 区第 1 位，查表得到“啊”。不过，实际解码器通常使用映射表，不一定逐步做这些运算。

这里的“国标码”“机内码”属于旧编码体系中的术语，资料中用法有时会比较宽泛；这套过程也不应直接等同于“Unicode 码点 → UTF-8”。

后来有 GBK 等扩展规范，可表示更多字符，并兼容 GB 2312 的常用表示。读取旧文件时仍需尽量确定它实际使用的是 GB2312、GBK、GB18030 还是其他编码，而不能只凭“中文编码”笼统判断。

## 4. Unicode 和 UTF：统一编号，再选择表示方式

Unicode 为大量文字和符号分配统一的**码点**。例如：

```text
A  → U+0041
中 → U+4E2D
```

UTF-8、UTF-16、UTF-32 都是把 Unicode 码点转换成代码单元或字节的编码形式。它们表示的是同一套 Unicode 数据，只是字节表示不同。[Unicode 标准：编码形式](https://www.unicode.org/versions/Unicode16.0.0/UnicodeStandard-16.0.pdf)

- **UTF-8**：每个码点占 1 到 4 字节；ASCII 范围占 1 字节，常用中文大多占 3 字节。

- **UTF-16**：大多数码点占 1 个 16 位代码单元，补充平面的码点占 2 个代码单元，也就是 4 字节。

- **UTF-32**：每个码点固定用 1 个 32 位代码单元，即 4 字节。

因此，UTF-32 不是因为“字符有时需要两个码元”才存在；需要代理对的是 UTF-16。Unicode 码点与人眼所见的字符也不总是一一对应：一个视觉上的符号可能由多个码点组合。

## 5. Java：字符串内部表示和外部 I/O 编码是两回事

### `char` 和 `String`

Java 的 `char` 是 16 位的 UTF-16 **代码单元**，并不总是一个完整的 Unicode 码点。较大的码点会用两个 `char`（代理对）表示。因此：

- `String.length()` 计算 UTF-16 代码单元数量。

- `String.toCharArray()` 返回 UTF-16 代码单元数组。

- `String.codePoints()` 可按 Unicode 码点处理字符串。

[Java `Character` API](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/Character.html)

### `String` 的内部优化

从 JDK 9 起，OpenJDK 的 Compact Strings 实现可以用 `byte[]` 保存 `String`：字符串全部能用 Latin-1 表示时，每个代码单元可用 1 字节存；否则使用 UTF-16 形式。Latin-1 覆盖 `U+0000` 到 `U+00FF`，ASCII 只是它的子集。这是 **JDK 的内部存储优化**，不会决定文件或网络输出使用哪种编码。[Oracle：JDK 9 Compact Strings](https://www.oracle.com/java/technologies/javase/9-relnotes.html)

### 外部输入和输出

读 GBK 文件时，指定 GBK 解码成 `String`；写 UTF-8 文件时，把 `String` 编码成 UTF-8 字节：

```java
String text = Files.readString(path, Charset.forName("GBK"));
Files.writeString(path, text, StandardCharsets.UTF_8);
```

Java 的 `Files.readString(path)` 不带编码参数时使用 UTF-8。较早的 Java API 默认编码可能取决于运行环境；JDK 18 及之后，Java API 默认字符集通常为 UTF-8。为了让字节结果明确，读写时最好显式指定编码。[Java `Files` API](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/nio/file/Files.html) [Oracle：默认编码变化](https://docs.oracle.com/en/java/javase/25/migrate/migrating-jdk-8-later-jdk-releases.html)

## 6. PowerShell：同样要看具体 I/O 边界

PowerShell 自己处理字符串时使用 Unicode 文本，但**控制台显示、管道传给原生程序、读写文件**可能采用不同编码。

- PowerShell 7 及之后的文本输出默认通常是 UTF-8 无 BOM。

- Windows PowerShell 5.1 的文件编码默认不统一：例如 `Out-File` 和 `>` 默认写 UTF-16LE，而 `Set-Content` 默认使用系统当前代码页。

- 控制台编码和文件编码也不是同一设置；`$OutputEncoding` 主要影响 PowerShell 把文本通过管道传给外部原生程序。

[Microsoft：PowerShell 字符编码说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-7.4)

遇到中文乱码时，要先确定问题发生在**文件读写**、**控制台显示**还是**程序间管道**，再检查对应环节的编码。

## 7. 乱码和“锟斤拷”

乱码通常不是字符本身坏了，而是某一环用一种编码产生字节，下一环却按另一种编码解释字节。

“锟斤拷”常见于这样的过程：

1. 字节按 UTF-8 解码失败，解码器用 Unicode 替换字符 `�`（`U+FFFD`）代替无法解码的部分。

2. `�` 用 UTF-8 编码后是字节 `EF BF BD`。

3. 两个这样的替换字符再被误按 GBK 解码：

```text
EF BF BD EF BF BD
→ 按 GBK 两字节分组：EF BF | BD EF | BF BD
→ 锟 | 斤 | 拷
→ 锟斤拷
```

`U+FFFD` 是 Unicode 标准中的通用替换字符。[Unicode 标准](https://www.unicode.org/versions/Unicode16.0.0/UnicodeStandard-16.0.pdf)

因此，“锟斤拷”常是**早先解码失败并替换内容**的线索。如果原始字节已经被替换字符覆盖，通常无法仅靠“锟斤拷”恢复原文；应寻找原始文件或备份。中断输出也可能让最后一个多字节字符被截断，但这和整段因编码错配而乱码是不同问题。

## 最后记住这三条

1. **码点是编号，UTF 是把 Unicode 编号表示成字节的方式。**

2. **Java `String` 的内部文本表示，不等于外部文件或控制台所用的编码。**

3. **每个字节流都要按它实际采用的编码来解码；写出时也要明确指定目标编码。**
