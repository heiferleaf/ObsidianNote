# `HDFS`分布式文件系统

大数据的时代，传统的文件存储系统，难以避免会碰到两个问题
- 扩容复杂：需要拆机
- 大数据量的读写效率低：只有一台机器进行读写（**单点IO瓶颈**）

分布式的存储系统，可以很好的适应大数据处理
- **容量问题**：通过横向扩容，容量不够就加机器，理论上没有上限
- **数据定位问题**：通过给文件加元信息，定位数据在哪个机器上
- **大数据存储问题**：把大文件切分成若干部分，分别存储在不同的机器上，并行存储（也通过元信息表示，每一块数据都在哪里）
- **数据副本**：给机器设置备份，简单有效的实现数据转储，防止硬件故障导致数据丢失（元信息表示每一份数据在哪些机器上有）

`Hadoop` 就是这样一个分布式的文件系统
- 是**横跨多台物理计算机**的存储系统
- 提供**统一的访问接口**，来对分布在多台机器上的存储文件进行访问和管理
	==因此，可以像使用一般的文件系统一样，使用分布式文件系统，感受不到任何差异==

`Hadoop` 也有一些特点是需要了解的，这决定的使用场景
- 支持数据的流式访问：会把数据看作流，从头到尾，完整的，顺序的传输。是 Write-Once-Read-Many（一次写入多次读取）：不支持随机写入数据，只能追加
- 适合处理大数据（高延迟、高吞吐）

> [!NOTE] 什么是流式访问
> 分布式存储里，“流式访问”的意思是：**一次写入，多次读取，每次读取都是“全表大扫描”**
> 它不支持“随机挑挑拣拣”（比如：你不能对 HDFS 说：“喂，把第 500 万行的那一个名字帮我改成张三”）。如果你想改，对不起，你必须把整个大文件全部读出来，改完再当成一个新文件写回去

# `HDFS` 提供的命令

> 基本上和 `Linux` 中的命令是一样的

随着版本的升级，提供的命令有所区别，现在还使用的方式有两种
- `hdfs dfs -命令 参数` ： 这种方式只支持本地文件系统和分布式文件系统中管理文件
- `hadoop fs -命令 参数` ：这种方式支持所有的文件系统，所有文件路径的参数，可以指定前缀 `文件协议://路径`，如果不指定，会使用 `core-site.xml` 中配置的 `defaultFS`

1. 创建文件夹
2. 文件夹中文件展示
3. 上传文件
4. 文件重命名
5. 文件移动
6. 下载文件
7. 追加写文件

```bash
# 创建文件夹
hadoop fs -mkdir -p /src/data

# 文件夹中文件展示
hadoop fs -ls -h /src/data

# 上传文件
hadoop fs -put local.txt /src/data/
# 或者用 -copyFromLocal
hadoop fs -copyFromLocal local.txt /src/data/

# 文件重命名
hadoop fs -mv /src/data/local.txt /src/data/new_name.txt

# 文件移动
hadoop fs -mv /src/data/new_name.txt /dest/data/

# 下载文件
hadoop fs -get /dest/data/new_name.txt ./
# 或者用 -copyToLocal
hadoop fs -copyToLocal /dest/data/new_name.txt ./

# 追加写文件
hadoop fs -appendToFile text.txt /dest/data/target.txt
```

# `HDFS` 的工作机制、流程

## 机制

- 主从架构
	- 主节点：`NameNode` ： 管理分布式文件系统的元数据，包含文件目录结构、文件位置信息、块信息、访问权限等等；提供
	- 从节点：`DataNode`： 实际存储文件的结点
	- 主节点辅助：`SecondaryNameNode` ： 帮助主节点完成元数据的合并工作
> 主节点不会把文件元信息持久化，只会在内存中组织；每一次从节点启动的时候，向主节点报告自己持有哪些文件的哪些块。
> 所以主节点一般内存比较大，从节点一般磁盘比较大

- 抽象的目录结构和元数据
	主节点维护的目录结构，组织文件之间的关系
	元数据包含文件的名称、大小、块大小，每一块所在的 `DataNode` 位置

- 数据分块存储
	- 分块才能支持对于大文件的并行读写

- 数据备份
	- 可靠性保证
	- 默认一份块，会有两个副本，总数是3
	> 但是在参数配置中，会把所有的数据块都当作副本，所以参数值为3，含义是总数为3


## 流程

> 客户端向分布式文件系统请求服务，处理的流程。
> 以创建文件为例子

1. 客户端创建 `DistributedFileSystem` 类对象 `dfs`，这个类封装了所有和文件系统交互的方法
2. `dfs.create()` ，底层通过 RPC 请求，向 `HDFS` 中的主节点，也就是 `NameNode` 发送请求
3. `NameNode` 检查创建的请求是否合法，客户端的权限是否合法，判断成功，就留下一条记录，返回客户端 `FSDataOutputStream` 流对象 `fsdos` 给客户端，用来写数据
4. 客户端通过 `fsdos` 写入数据
	1. 从 `NameNode` 获取数据分块的块大小
	2. 数据拆分为若干的数据包，每一个数据包写的时候，内部通过 `DataStreamer` 向 `NameNode` 请求存储数据的 `DataNode`，默认3副本
5. 数据在 `DateNode` 之间，以 `Pipeline` 管道方式传输
	- ==管道传输，充分利用结点的磁盘IO和网络IO，效率高==
6. 和传输方向相反，发送 `ack` 请求
	- ==通过ack机制，保证数据传输的可靠性==
7. 数据写完， `fsdos.close()` 关闭
8. `dfs` 告知 `NameNode` 文件写入完成，等待其确认
	- 通过客户端收到 ack 的情况，比较自己的**最小复制数**，如果副本保存成功结点数量大于等于，向客户端回复确认，然后后台异步补齐缺失的副本


> 客户端向主节点确认要写入，相当于请求权限
> 客户端得到授权之后，写入数据，客户端内部处理分块，主节点提供副本是哪些
> 客户端写入第一次结点，然后DateNode1在写入数据的同时，通过网络通信，让DataNode2写...
> 客户端在向主节点汇报，主节点检查写入情况，成功则流程结束
