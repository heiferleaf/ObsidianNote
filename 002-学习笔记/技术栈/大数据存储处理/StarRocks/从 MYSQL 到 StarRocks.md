> StarRocks 是列式存储数据库，设计特点决定了其适合作为大规模数据的数据库

# 建立数据表

相比于 MySQL 的数据建表， StarRocks 的建表会根据**使用数据的业务特点**来决定建表方式。具体来说，数据库中的存储的数据模型可以分为四种

## 明细模型

和一般的关系模型等价，存储最原始、完整的数据。

适合存放**日志、流水**

## 聚合模型

聚合模型的数据结构中，会指定用于聚合的列，和具体聚合的列；在数据操纵中，数据的插入操作会直接聚合（如累加、求最大、最小）

适合做**报表、统计**

## 更新模型 & 主键模型

考虑到列式存储的数据库修改数据开销比较大，引入这两个模型。

数据结构定义：会指定一个 key，key相同的数据认为是同一行的数据，新的数据会直接覆盖老的数据
- **更新模型**：用的是“读时合并”策略。数据写进去时先堆着，等你 `SELECT` 查询的时候，它在后台现场去重，把最新的那条吐给你。缺点是：查询时比较费 CPU。
- **主键模型**：用的是“写时合并”策略。数据写进去的瞬间，它就在内存里通过索引锁定了老数据的位置，直接把新数据接管过来。缺点是：非常吃内存。

> [!NOTE] 开销的改进
> 
> MySQL 是行存储的数据库，并且存储处理的数据量不会很大（千万级别）。这种前提下，通过 B+ 树组织的索引文件可以较快的定位数据，并且行数据一般在同一个磁盘快中，IO读取次数较小。
> 
> StarRocks 在这种场景下，开销比较大，因为
> - 数据量大，上亿，定位数据会比较慢
> - 更重要的是，列式存储决定了修改数据行需要把分散的每一个列文件都读取到内存中，磁盘IO次数多
>   
> 而合并的思想，不是直接修改原来的数据行，而是先办法认为新的数据行有效，原来的无效。
> 更新模型的做法：直接在列文件后追加写（速度快），读操作发生时，对比key相同数据的版本号或者时间戳，决定更加新的数据，所以说查询的时候吃 cpu 运算比较
> 主键模型的做法：在内存维护每一行数据对应的索引号（列文件中都是对应存储的），写入数据时，先追加写，然后标记原来的数据行索引为失效，指向新数据，所以说吃内存

## 分区分桶表

和 Hive 中的思想一致，通过把数据进行显示的分区，或者根据字段哈希取模分桶，实现数据操作时，能更有针对性的操作实际需要的数据，加快速度

# 数据导入

StarRocks 不支持单条数据的插入

大数据系统的写入核心原则是：**攒批（Batching）**。要么在后端攒够了一起写，要么让专门的中间件去源源不断地倒进去。

- **Stream Load（HTTP 传输）：** 这是 Java 后端最常用的方式。你写一个定时任务，把业务系统里积攒的 1 万条日志导出成一个 JSON 或 CSV 字符串，然后直接用 Java 发一个 **HTTP PUT 请求** 砸给 StarRocks。 StarRocks 收到这个请求后，在内存里把这 1 万条数据一次性夯实成一个 `.dat` 文件。高效，干净。
    
- **Routine Load（对接 Kafka）：** 你的微服务系统只需要负责把业务消息（比如订单创建）源源不断地丢进 **Kafka 消息队列**。 你在 StarRocks 里敲一行命令，让它自己去当 Kafka 的消费者。StarRocks 会自己默默地在后台拉取消息，每隔 5 秒钟或者每满 10 万条数据，自动在底层结账（夯实）一次。

# 事务控制

不支持细粒度的锁控制，和一般操作的事务管理。

支持对导入操作的事务控制 ACID
