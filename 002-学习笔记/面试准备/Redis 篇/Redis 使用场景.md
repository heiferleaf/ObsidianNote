> [!NOTE] # Redis 作为缓存时的问题

参见笔记 [[002-学习笔记/零碎知识笔记/Redis 雪崩、击穿、穿透防护|Redis 雪崩、击穿、穿透防护]]

这里回顾一下之前不会经常思考的方案：

1. **缓存穿透**：高频访问到不存在的数据，访问穿过缓存，达到了数据库
	1. 设置控制
	2. 布隆过滤器
	   在架构中位置：布隆过滤器通常设置在对请求的第一层处理中，通过数据的key来判断请求数据是否一定不存在于数据库中，从而过滤部分无效请求
	   生效流程：
		   - 初始化时：除了缓存预热，还需要把数据库中数据的key批量写入布隆过滤器
		   - 新增数据库数据时：除了同步缓存状态，还需要更新布隆过滤器
		   - 请求到来时：有布隆过滤器做一次“确定性排除”，将一定不在数据库中的数据请求拦截，减轻下游压力
		布隆过滤器的缺陷：
		    - 误报：对于不在数据库中的数据请求，可能会拦截失败
		    - 不支持删除：数据库中数据删除，无法对布隆过滤器做删除操作
		    - 数据量变多后，布隆过滤器的过滤效果下降，需要重建扩容
		总结：布隆过滤器利用极小的空间成本，在缓存前加入了一道“确定性过滤”，将部分无效的请求直接拦截栏请求层。缺点是会误判、不支持删除、需要定时重建
	3. 参数校验

2. **缓存击穿**：缓存热点数据过期，导致大量请求一时间打到数据库
	- 逻辑过期方案：查询缓存-》得到数据-》检查出过期-》加分布式锁（失败返回旧数据）-》交给另一个线程B从数据库获取数据更新缓存-》线程B释放锁-》原线程返回旧数据
		- **优点**: 当第一个线程去尝试更新缓存数据，之后的线程直接返回旧数据，第一个线程把更新行为交给另一个线程也返回旧数据 -》响应时间短
		- **缺点**：数据一致性弱，发现逻辑过期后，还是会拿到旧数据
	- 分布式锁方案：一致性强，保证过期了拿到新数据；对应响应时间长


3. **缓存雪崩**
	1. 采用本地缓存，形成多级缓存，防止 Redis 崩溃
	2. 随机时间...


> [!NOTE] # 缓存和数据库数据的一致性


1. 这个问题首先取决于缓存的读写模式，讨论 Cache Aside 架构下

2. 先更新数据库，后删除缓存
	- ==为什么删除缓存而不是更新？==
		- 多线程并发时，更新写操作可能引入脏数据
		- 删除缓存，意味着后续当数据真正被使用，才会进入缓存，符合缓存空间换时间的前提是缓存数据会被访问
	- ==顺序为什么是先数据库，后缓存==
		- 先缓存删除，后数据库更新，只要有读线程，读取行为在 _缓存删除和数据库更新之间_， 就会导致脏数据的回写；或者当读线程读缓存时缓存的数据过期，下一步读数据库的行为发生在数据库更新之前，也会导致脏数据回写
		- 先数据库更新，后删除缓存，脏数据概率比较小，需要满足
			1. 读缓存的时候数据过期
			2. 读数据库在写数据库之前
			3. 回写缓存在删除缓存之后
	

3. 2 的基础上，采用**延迟双删**
	1. 延迟多久不好控制

4. 利用读写锁的思想，
	- 控制**更新数据库**行为发生时，读取操作互斥
	- 优点：没有脏数据的可能了
	- 缺点：适合读多写少，读写的冲突会影响响应延迟

5. CDC 方案，通过监听数据库变化，或者通过本地消息表、事务消息，实现缓存数据和数据库数据的最终一致性
	1. 有脏数据
	2. 更新数据库和更新缓存解耦
	3. 缩短响应时间
	4. 利用消息队列，保证可靠执行


> [!NOTE] # 缓存数据如何不丢失（持久化）

**RDB（Redis Database backup，Redis数据快照）、AOF（Append Only File，追加文件）**

RDB 
- 保存当前内存完整的数据内容
- 保存所需的时间较长，两次保存之间的数据可能会丢失
- 文件内容比较小，恢复数据方式是直接写入内存，速度比较快
- 可以fork一个子线程完成RDB备份 
	- 子线程备份过程中，父线程修改数据，会触发COW，对子进程备份无影响
	- 使用子进程备份：备份过程中，实际数据就会产生差异 `bgsave`
	- 不使用子线程备份：备份过程中，Redis不可用

AOF
- 保存的完整的Redis写指令
- 保存指令内容比较快（追加写文件），所以可以配置
	- 实时刷新：每一条写指令都同步文件
	- 秒刷新：每一秒同步一次文件
	- 操作系统管理
- 文件内容是完整的指令，文件比较大，恢复数据方式是重做命令，速度比较慢
- 为了减少文件大小，针对同一个key数据的写命令，可以通过 bgrewriteof 命令重写 aof 文件，仅保留最后有效的写命令
	- 可以配置自动触发重写，配置项
		- aof 文件大小达到多少大
		- aof 文件大小增长了百分之多少

两者可以配合使用，在保存 RDB 的时间里，使用 AOF 记录命令


> [!NOTE] # 缓存数据过期，如何计算删除

**惰性删除**

和逻辑过期想法类似，不会主动删除过期的数据，而是在数据被访问的时候检查是否过期，过期则删除数据。

**定期删除**

后台线程跑定时任务，从数据库中抽取随机数据，检查这些数据在缓存中是否过期，过期删除
- SLOW
- FAST
> 两种策略在于定时任务的频率

一般两种结合使用


> [!NOTE] # 缓存的内存满了，如何淘汰缓存数据

Redis 提供了8种策略：
- noeviction（**默认**）：不淘汰数据，内存满了就不支持写入数据操作，报错
- always:
	- always-random：对全体数据，随机淘汰
	- always-lru：对全体数据，淘汰最近最久未使用
	- always-lfu：对全体数据，淘汰最近最少使用
- volatile:
	- volatile-ttl：对设置了过期时间的数据，选择剩余时间最少的淘汰
	- volatile-random：对设置了过期时间的数据，随机淘汰
	- volatile-lru：对设置了过期时间的数据，淘汰最近最久未使用
	- volatile-lfu：对设置了过期时间的数据，淘汰最近最少使用

> 1. 如果业务有冷热数据区分（有经常访问的数据），建议采用 lru
>  2. 如果业务有置顶数据的需求，建议使用 volatile，置顶数据不设置过期时间


> [!NOTE] # Redis 分布式锁

1. 使用 Redisson 锁，默认是可重入锁
	- Hash 结构，key - field - value，其中 field 为 threadId，value 为重入次数
2. 锁需要能过期，防止持有锁线程宕机导致锁无法释放
3. setnx获取锁，对应释放锁不能直接 DEL，防止锁过期误删除别人的锁，要用 LUA 脚本把判断线程+删除锁原子化
4. 为了防止让线程执行时锁过期，导致并发冲突，引入看门狗机制
```java
	Redission lock = xxx;
	lock.tryLock(time_1,尝试获取锁时间，time_2锁过期时间， key)
	
	// 1. time_2 =  -1 || 不传入：使用看门狗，检测线程是否还在执行
```
5. **主从一致**
   锁本身也是数据，当 Redis 采用主从架构，使用默认的异步复制策略时，主节点宕机，并且锁没有同步到从节点，选出的新的从节点可能会导致重复加锁。
   这说明 Redis 集群采用 AP （在CA中选择A），如果业务对于一致性有要求，可以只用 ZooKeeper


> [!NOTE] # Redis 架构


**Redis 主从架构**

主节点和从节点，从节点的数据如何和主节点保持一致性

采用==全量和增量方式同时使用==
1. 从节点主动向主节点发送请求，附带（replication id，offset）
2. 主节点判断从节点是否第一次发送请求
3. 如果第一次发送请求
	1. 响应自己当前的版本信息（replication id， offset）
	2. 主节点执行bgsave，生成rdb文件，发送给从节点
	3. bgsave期间的命令记录到一个日志文件中，发送给从节点
4. 如果不是第一次发送请求同步数据
	1. 主节点获取从节点的 offset
		1. 对比自己的offset，如果自己的更大，同步这期间的命令日志

> [!NOTE] # Redis 哨兵

哨兵用于在主从架构中，保证故障的恢复（选取新的主节点），实现集群的高可用

哨兵结点三个作用
1. 监控主从结点
2. 选取新的主节点
3. 向客户端通知集群内部结点状态

**监听**
- 通过 ping，验证结点是否存活
- ping 超时的数量达到 quarom，认为结点挂了

**选取主节点**
- 从节点之前和主节点的通信时间不能太长
- 比较结点的优先级，高的优先
- 同优先级比较 offset，大的优先
- 同offset比较结点id，小的优先

**通知客户端**
	当出现网络分区，主节点和哨兵、从节点网络不通，哨兵选取新的主节点（相当于此时有两个master）、通知客户端期间，客户端向master写的数据会丢失。
	为了防止这个问题，采用配置
	- 主节点的从节点最小数量，如果master连接的slave太少，不响应客户端命令
	- 主从复制数据延迟最大时间，超时不响应
