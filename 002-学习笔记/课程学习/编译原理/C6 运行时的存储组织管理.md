# 运行时存储组织管理核心笔记

## 1. 运行时内存全局划分

### 1.1 代码区与数据区静态划分

- **代码区（Code Area）**：存放编译后生成的机器指令。在运行期该区域通常只读，以防止程序意外自我篡改。
    
- **静态数据区（Static Data Area）**：存放全局变量和编译期即可确定生命周期、大小的静态变量（如带有 `static` 关键字的变量）。其内存地址在编译期由编译器直接锁死，运行期不发生位置偏移。
    

### 1.2 栈区与堆区的动态对撞生长模型

- **栈区（Stack Area）**：用于管理函数调用的活动记录（AR）。其空间分配严格遵循后进先出（LIFO）原则，随函数的调用而动态压栈，随函数的返回而自动弹栈销毁。
    
- **堆区（Heap Area）**：用于管理运行期动态申请的、生命周期不确定的内存块（如 `malloc`、`new` 申请的空间）。
    
- **物理模型**：为最大化利用虚拟地址空间，栈区通常从高地址向低地址向下生长，堆区从低地址向高地址向上生长，两者在未分配的空白中心区域进行动态对撞。
    

### 1.3 编译期与运行期的权衡边界

- **编译期（Static Time）**：编译器在纸上分析代码文本。此时能够确定的属性包括局部变量在栈帧内的**相对偏移量（Offset）**、名字的嵌套深度、非局部变量的词法所属。
    
- **运行期（Runtime）**：程序实际加载进物理内存执行的阶段。此时才能确定栈帧的物理绝对基地址、递归调用中具体存活的实例个数、以及动态堆内存的物理分配。
    

## 2. 块结构变量空间分配与重叠（针对无局部过程语言）

### 2.1 块结构局部作用域定义

在诸如 C 语言等不允许函数嵌套定义的过程式语言中，函数内部可通过大括号 `{ ... }` 划分出相互并列或嵌套的**局部块（Block Structure）**。块内部声明的变量其生命周期与该块的执行期严格绑定，出块即失效。

### 2.2 编译期虚拟指针 TOS 算账逻辑

- **TOS (Top Of Stack)**：是编译器在编译阶段用于跟踪和计算当前局部变量区已分配空间底端边界的**虚拟计数器**，而非运行时的 `SP` 寄存器。
    
- **递推分配规则**（假设栈向下生长，地址减小，`int` 占 4 字节）：
    
    1. 遇到变量声明 `int x;`，令 `x.offset = TOS`。
        
    2. 随即更新计数器：`TOS = TOS - 4`。
        

### 2.3 互不嵌套并列块的空间重叠复用算法

当函数内部存在两个互不嵌套的并列块（如块1 和块2）时，由于块1 的执行期与块2 完全互斥，块1 退出后其内部变量已死。编译器利用虚拟指针的复用算法压榨栈空间：

1. 进入块1 前，记录当前的 `TOS` 值为 `OLD_TOS`。
    
2. 在块1 内部按照递推规则正常分配变量空间，`TOS` 持续减小。
    
3. **退出块1 时，编译器强制执行 `TOS = OLD_TOS`（恢复现场）。**
    
4. 进入块2 时，新变量直接从恢复后的 `OLD_TOS` 位置重新开始分配。
    

- **物理本质**：块1 的局部变量与块2 的局部变量在同一个活动记录的局部变量区中**物理空间完全重叠**，实现内存复用。
    

### 2.4 嵌套块与并列块的偏移量计算差异

- **并列块**：满足空间重叠复用条件，各并列块内部首个声明变量的 `offset` 相同。
    
- **嵌套块**：外层块包裹内层块。当执行内层块时，外层块的变量依然存活，空间不可重叠。内层块变量的 `offset` 必须在外层变量分配完的 `TOS` 基础之上继续向下累减。
    

## 3. 过程活动记录（AR / 栈帧）布局与底层设计

### 3.1 活动记录（Activation Record）的标准物理结构

一个完整的运行期活动记录（又称栈帧，Frame）在内存中通常包含以下连续物理字段（从高地址到低地址）：

1. **实参区（Actual Parameters）**：存放调用方传进来的参数值或参数指针。
    
2. **返回值区（Returned Values）**：为函数返回值预留的临时存放空间。
    
3. **控制链（Control Link）**：又称动态链（Dynamic Link），存放调用方（Caller）的栈帧基地址。
    
4. **访问链（Access Link）**：又称静态链（Static Link），用于支持过程嵌套语言跨层访问非局部变量。
    
5. **状态保存区（Saved Machine Status）**：保存调用发生前的 CPU 寄存器（如 PC、返回地址 RA 等）状态，以便返回后恢复现场。
    
6. **局部变量区（Local Variables）**：存放本函数内定义的、编译期可确定大小的局部变量。
    
7. **临时变量区（Temporary Variables）**：存放表达式计算中间结果（如 $\text{a} + \text{b} \times \text{c}$）的临时寄存器溢出值。
    

### 3.2 基址指针 FP 与栈指针 SP 的解耦寻址关系

- **SP（Stack Pointer）**：始终指向当前栈区的绝对栈顶。由于函数执行过程中临时变量频繁压栈出栈，`SP` 的物理数值处于高频动态抖动中。
    
- **FP（Frame Pointer）**：在函数初始化完成后保持绝对静止，死死指向当前栈帧的一个固定基准位置（在 x86 中即为 `EBP`）。
    
- **寻址公式**：由于 `SP` 动态在变，编译器在早期的语法分析阶段无法以 `SP` 为基准算账。因此，栈帧内所有元素的访问统一解耦为静态相对寻址：
    
    $$\text{物理绝对地址} = \text{FP} \pm \text{offset}$$
    
    其中参数通常位于 $\text{FP} + \text{offset}$（高地址侧），局部变量位于 $\text{FP} - \text{offset}$（低地址侧）。
    

### 3.3 参数反向压栈（右至左）的底层技术因果

在 C 语言标准（如 `cdecl` 调用约定）中，参数必须从右向左反向压入栈中。其技术原因有二：

1. **支持可变参数（如 `printf`）**：反向压栈可以确保函数代码中写在最左侧的第一个参数（形参列表里唯一的固定参数，如格式化字符串 `"%d %f"`）在物理上**永远最后入栈**。这意味着它在运行期的物理位置必然距离 `FP` 最近且相对偏移量绝对固定。函数一进入即可优先读取该参数，从而解析出后续还有多少个变长参数。
    
2. **包容老旧编译器的不检查特性（R&C 历史遗留）**：即使调用方故意多传或少传了尾部参数，第一个参数和前序参数相对于 `FP` 的寻址偏移位置也绝不会发生错位挪动。
    

### 3.4 `-fomit-frame-pointer` 编译器优化开关

- **原理**：若开启此 GCC 优化选项，编译器在最后阶段会强行干掉 `FP` 寄存器（将其释放为普通通用寄存器参与算术运算），转而通过复杂的编译期后端算法，计算出每一条指令处 `SP` 相对于栈底的精确差值，完全用 `SP ± offset` 寻址。
    
- **代价**：该优化虽能提升少许运行效率，但会导致运行时物理栈帧边界模糊，调试器（如 GDB）无法轻松通过读取旧 `EBP` 来追踪（Backtrace）调用栈，使程序调试极度困难。
    

## 4. 词法作用域与环境嵌套深度

### 4.1 最紧嵌套规则与名字遮蔽

- **最紧嵌套规则（Most Closely Nested Rule）**：名字的作用域范围在其被声明的那个过程（或块）内部完全可见，同时对其内部所有深层嵌套的子过程（或子块）同样默认可见。
    
- **名字遮蔽**：若内层过程声明了一个与外层过程完全同名的变量，则在外层变量在内层执行期被“遮蔽”不可见，遵循就近原则访问内层变量。
    

### 4.2 环境嵌套深度（Embedding Depth）的静态数值定义

- 显式规定：程序中最外层的主程序（`MAIN`）静态嵌套深度定义为 $1$。
    
- 每向内层直接新定义（直接包裹）一个子过程，该子过程的静态嵌套深度即增加 $1$。
    
- 嵌套深度值在编译期阅读代码时即可唯一确定，属于名字的静态空间拓扑属性。
    

### 4.3 运行时活动树与静态嵌套树的映射

- **静态嵌套树**：反映的是代码在文本上的空间包裹关系，它是绝对死板、不可变的。
    
- **活动树（Activation Tree）**：反映的是程序跑起来后，各个函数在时间线上的动态调用历史。
    
- **映射定理**：动态活动树的任意一条分支路径上同时存活的函数实例，其名字的可见性与解析，必须死死遵循静态嵌套树的词法约束。
    

## 5. 四种参数传递机制的物理本质与运行期演算

### 5.1 传值调用 (Call by Value)

- **物理本质**：**彻底的副本拷贝。**
    
- **运行期行为**：调用方计算出实参的当前表达式值，并将其复制一份写入被调方 AR 的形参格子中。形参和实参在内存中处于完全独立的两个物理格点。函数内部对形参的任何写操作只改动本栈帧内的副本，函数返回后栈帧销毁，对外部实参毫无影响。
    

### 5.2 传引用调用 (Call by Reference)

- **物理本质**：**传递实参的物理内存地址（指针传递）。**
    
- **运行期行为**：调用方将实参的绝对物理内存地址压入栈中。在被调函数内部，任何对形参的读写指令，在硬件级都会被自动转化为**间接寻址指针操作**（即 `MOV R1, [形参指针]`）。形参实质上成为了实参的物理别名，函数内对形参的修改会**实时、同步**地体现在外层实参中。
    

### 5.3 传值返回调用 (Call by Value Result / Copy-Restore)

- **物理本质**：**进时拷贝值，出时拷贝回的双阶段动作。**
    
- **运行期行为**：
    
    1. **进入函数时**：执行类似于 `Call by Value` 的动作，将实参的值拷贝给形参。在函数运行期间，形参与全局/外层实参互不干扰，各自独立。
        
    2. **退出函数前的最后一刻（恢复序列）**：被调函数执行退出前，通过硬编码指令，把形参此时的最终数值，**反向强制复制回**实参所在的物理内存空间中。
        
- **全局变量覆盖陷阱**：若将一个全局变量作为实参传给该函数，且函数内部在中途通过全局变量名直接修改了该全局变量，则在函数返回的最后一刻，形参的最终值依然会无情地反向覆盖（Overwrite）掉该全局变量中途改变的值。
    

### 5.4 传名调用 (Call by Name)

- **物理本质**：**文本无脑替换与延迟求值（Lazy Evaluation）。**
    
- **运行期行为**：形参在编译期被当做宏文本，整体直接替换为实参的代码文本串。在函数内部，只有每一次真正执行到该形参所在的语句时，CPU 才会现场重新计算该替换文本的当前数值。
    
- **数组下标动态错位陷阱**：若实参为 `A[i]`，若函数体内某行代码修改了 `i` 的值，那么在修改语句之后再次读写形参时，由于文本延迟求值，实际触达的内存目标会动态改变为修改后的 `i` 所对应的全新 `A[i]` 元素。
    

### 5.5 语言特例辨析：C 与 Java 数组传参在栈/堆中的物理模型

- **C 语言普通数组传参**：其本质依然是 `Call by Value`。但由于 C 语言中“数组名自动退化为首元素指针”的语言特性，其拷贝进去的“值”是一串**物理内存首地址**。因此，在函数内部执行 `形参 = 新数组地址` 时，仅仅是改变了本栈帧内该形参指针变量的指向，外层原数组名对应的物理空间不受任何影响。
    
- **Java 数组传参**：Java 的数组是堆（Heap）上的对象，数组变量本质上是存储该堆块首地址的引用变量。当作为参数传递时，Java 复制了该引用变量的值（即堆内存地址）。在函数内执行 `形参引用 = 新数组对象`，改变的也只是局部栈帧内形参变量本身的数值，外层引用指向的堆块依然保持不变。
    

## 6. 源语言特征决定存储分配策略定理

### 6.1 静态分配（Static Allocation）的前提限制与局限

- **策略特性**：编译期彻底固定所有名字的物理内存绝对地址。
    
- **语言特征约束**：
    
    1. **绝对不允许递归调用**（因为递归意味着同一过程的多个实例必须同时存活，而静态分配下该过程在内存里只有一个活动记录空间，多实例存活会导致数据空间相互覆盖污染）。
        
    2. 局部变量在过程结束后其值必须默认保留（类似 `static`）。
        
    3. 所有数据类型的大小在编译期必须绝对固定，不能有动态数组或动态内存申请。
        

### 6.2 栈式分配（Stack Allocation）的后进先出物理约束

- **策略特性**：每次函数调用动态压栈生成 AR，返回时动态销毁。
    
- **语言特征约束**：
    
    1. **必须支持递归调用**。
        
    2. 局部变量的生命周期与过程的调用期严格绑定，过程一旦结束，局部变量随栈帧销毁直接消亡。
        
    3. 语言结构**不允许**出现“内部嵌套过程作为返回值返回（闭包）”的一等公民特性，否则会导致栈帧销毁后的内存悬空问题。
        

### 6.3 堆式分配（Heap Allocation）的引入边界条件

- **策略特性**：内存块在托管堆上任意分配，生命周期由垃圾回收机制或程序员手动显式释放控制。
    
- **语言特征约束**：
    
    1. 语言支持显式的动态内存申请（如 `malloc`、`new`）。
        
    2. 语言具有函数式一等公民特征，**允许过程内嵌套定义的子过程作为返回值返回**（即激活了闭包机制）。
        

## 7. 跨层非局部变量访问方案 A：访问链（静态链）机制

### 7.1 访问链（Static Link）与控制链（Dynamic Link）的物理隔离

在支持过程嵌套的语言中，每一个动态栈帧内部必须并行维护两根完全不同的指针链：

- **控制链（Dynamic Link）**：由底层标准的 `push ebp` 汇编指令产生。它指向的是**谁调用了我**。用于函数返回时恢复调用者的旧 `FP` 现场。它反映的是运行期的动态调用历史。
    
- **访问链（Access Link）**：由编译器额外开辟的空间维护。它指向的是**在代码文本中直接包裹当前过程的词法外层过程的最新活动记录基地址**。它反映的是写死在纸上的词法嵌套树关系。
    

### 7.2 过程调用可见性三大判定规则

假设当前过程为 $X$，其直接嵌套定义了子过程 $P$ 和 $Q$，而 $P$ 内部又嵌套定义了 $R$：

1. **平级与自我调用合法**：过程 $X$ 可以递归调用 $X$ 自身；$P$ 和 $Q$ 作为同层兄弟，在内部可以互相 `Call` 调用。
    
2. **向内直接调用合法**：外层过程 $X$ 拥有调用其直接内层亲儿子过程 $P$ 或 $Q$ 的权限。但 $X$ **没有**权限跨层去调孙子过程 $R$。
    
3. **向外词法包裹调用合法**：最内层的孙子过程 $R$ 有权去 `Call` 调用直接包裹它的父亲 $P$，也有权去调用间接包裹它的爷爷 `MAIN`，或者调用与父亲平级的叔叔 $Q$。
    

### 7.3 静态链寻址数格子递推公式

当嵌套深度为 $n_p$ 的当前活跃过程 $P$，试图去访问一个声明在嵌套深度为 $n_x$ 的外层环境中的非局部变量 $X$ 时（必须满足词法可见性前提 $n_p \ge n_x$）：

- **间接寻址步数公式**：
    
    $$\text{指针追踪次数} = n_p - n_x$$
    
- **执行过程**：
    
    - 若差值为 $0$，说明是局部变量，追踪 $0$ 次，直接在当前栈帧寻址。
        
    - 若差值为 $1$，说明在亲爹环境，CPU 只需读取当前 AR 的 `access link` 字段 $1$ 次，即可跨入亲爹栈帧。
        
    - 若差值为 $2$，说明在爷爷环境，CPU 需顺着当前 `access link` 跨出第一步到亲爹栈帧，再提取亲爹栈帧内的 `access link` 跨出第二步，方能触达爷爷栈帧。
        

## 8. 跨层非局部变量访问方案 B：DISPLAY 表（层数表）优化机制

### 8.1 静态链长距离寻址性能瓶颈原因

当代码静态嵌套层次较深（例如 $n_p - n_x \ge 3$）且跨层非局部变量访问极其频繁时，静态链机制迫使 CPU 必须在运行期执行多级高频的间接指针跳转寻址。这种“顺藤摸瓜”的链式追踪无法保障时间复杂度在 $\mathcal{O}(1)$，严重拖慢内存访问效率。

### 8.2 DISPLAY 全局指针数组的物理本质

DISPLAY 表是一个由运行时环境维护的全局指针数组（记为 $d$），其最大长度等于当前程序的最大静态嵌套深度。

- **核心映射机制**：数组的下标 $k$ 与静态词法嵌套深度 $k$ 完全强对齐。
    
- **物理含义**：在运行期的任意时间点，全局数组项 $d[k]$ 中存放的指针，**永远死死指向当前栈（或堆）中距离栈顶最近的、嵌套深度为 $k$ 的那个活跃过程实例的活动记录基地址**。
    
- **硬件级优化**：由于其规模极小且高频读写，编译器在生成机器码时会优先将其塞进 CPU 的高带宽通用寄存器组中。
    

### 8.3 编译期对引用下标的静态确定与硬编码

- **符号表透视**：任何一个非局部变量 $x$，在编译阶段的符号表中就已经静态记录了其被声明时所在的精确嵌套深度 $k$。
    
- **硬编码常数化**：编译器在编译到访问该变量的语句时，根本不需要在运行期动态计算它的深度。编译器直接将常量值 $k$ 作为数组的立即数下标硬编码进目标查表指令中：
    
    $$\text{Target\_Address} = d[k] + \text{offset}_x$$
    
    运行时 CPU 无需任何链式循环计算，直接通过硬编码下标定位 $d[k]$，一步到位直接寻址。
    

### 8.4 运行时 DISPLAY 表的动态维护算法

当程序发生过程调用进入或退出时，为了维持 $d[k]$ 始终指向最新有效环境的定义，必须动态改写表项。

#### A. 过程调用进入阶段（深度为 $k$ 的新过程实例诞生时）

1. **备份老现场**：在新 AR 初始化期间，将当前全局 DISPLAY 表中已经存在的旧指针 $d[k]$ 取出，妥善备份到新 AR 内部特设的 `access link` 字段格子里。
    
2. **新主登记**：将这个刚刚诞生的新 AR 的绝对物理基地址，强行写入全局 DISPLAY 表的 $d[k]$ 中，完成对老环境的覆盖投屏。
    

- _算法公式_：
    
    $$\text{New\_AR.access\_link} = d[k]$$
    
    $$d[k] = \text{New\_AR.base\_address}$$
    

#### B. 过程返回退出阶段（深度为 $k$ 的过程实例销毁时）

1. **提取备份**：在该 AR 被销毁弹出前的最后一刻，从其内部 `access link` 字段中提取出当初进入时备份的老环境指针。
    
2. **反向改写还原**：将该备份指针重新写回全局 DISPLAY 表的 $d[k]$ 项中，使墙上的显示器自动回滚恢复为上一个最近存活的深度为 $k$ 的环境。
    

- _算法公式_：
    
    $$d[k] = \text{Current\_AR.access\_link}$$
    

## 9. 动态内存管理崩溃：悬空引用与闭包底层形态

### 9.1 悬空引用的成因定义

- **科学定义**：当一个过程执行结束执行了释放（Deallocation）动作，其栈帧空间已被宣告死亡并允许后续程序覆盖。如果此时该过程将内部局部变量的物理内存指针作为返回值交给了外部，外部程序后续通过该指针再次发起读写，即触发**悬空引用（Dangling References）**。
    
- **物理本质**：内存空间**释放在前**，外部指针**引用在后**，导致触达被污染的脏数据或引发段错误。
    

### 9.2 局部过程作返回值对纯栈式分配的解构缺陷

当语言支持“在过程内部定义子过程，并允许将该子过程作为返回值返回（一等公民函数）”时，子过程内部可能死死绑定了外层父过程的非局部变量。

- **栈式破产原因**：按照后进先出规则，父过程一旦返回，其栈帧必须在物理上整体销毁弹出。然而被返回的子过程在后续任意时刻都可能被外部调用，此时它顺着静态链或环境指针去栈里找父过程的变量，发现原栈帧早已死亡或被新函数污染。**因此，纯栈式内存管理在此类特征下直接宣告破产。**
    

### 9.3 闭包（Closure）在堆上的物理构成

为了彻底解决上述悬空引用缺陷，凡是支持该特性的现代语言（如 JavaScript、Python、Go），其活动记录**不再存放在栈上，而是直接在堆（Heap）上分配**。

当外层函数返回子函数时，运行时环境将其打包为一个从堆中独立申请的复合结构，称为**闭包（Closure）**。其物理构成满足以下精确定义公式：

$$\text{闭包 (Closure)} = \text{函数代码指针 (Code Pointer)} + \text{环境指针 (Environment Pointer)}$$

- **函数代码指针**：指向 Code 段中子函数的静态机器指令入口。
    
- **环境指针**：死死指向刚才外层父函数在堆（Heap）上开辟的那个活动记录块。
    

### 9.4 托管堆活动记录的生命周期与 GC 依赖

- **生命周期解耦**：由于活动记录分配在堆上，其生命周期不再受“后进先出”的时间线限制。即使外层父函数已经执行完毕退出，只要被返回出来的闭包依然被外部全局变量或引用拉扯着，其环境指针指向的父函数堆块就**绝对不会被销毁**。
    
- **GC 依赖**：该活动记录的最终销毁，完全脱离了函数返回的时机，而是转而依赖运行时环境的垃圾回收器（Garbage Collector）通过可达性分析（Reachability Analysis）算法进行异步的主动打标与回收。
