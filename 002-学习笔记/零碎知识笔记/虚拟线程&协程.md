> 把视角切到操作系统除了线程运行机制。
> 多对一映射：用户态函数调度线程（ULT），优点是调度开销小，缺点是进程一个线程的阻塞操作，直接导致进程被阻塞
> 一对一映射：线程的调度全权由内核负责，优点是并发/并行程度高，缺点是线程调度开销涉及到cpu状态切换，开销大
> 多对多映射：两者结合，但还是存在问题，当一个线程阻塞，其绑定的KLT上的其它ULT也无法执行，其二就是ULT和KLT两套调度机制，实现起来很麻烦

# 虚拟线程

在较新的 JDK 版本中，用户创建的线程**ULT**和内核级线程**KLT**是一对一映射，调度由操作系统内核负责，涉及到处理器状态的切换和上下文的保存恢复。

为了减小调度的开销，同时保证进程的多线程并行/并发处理能力，借助多对多映射的思想，多个用户线程绑定一个内核线程，同一**KLT**对应的**ULT**调度，由用户库函数负责。
这里多个ULT，就是**Java**支持的虚拟线程。每一个虚拟线程都是堆区中的对象，保存**PC寄存器，函数调用栈**。多个虚拟线程绑定到同一个负载线程，也就是原本和内核线程一对一的用户线程，负载线程记录虚拟线程的运行状态，在虚拟线程需要调度的时候，可以进行上文的保存和恢复。

为了克服多对多映射方式的缺陷：线程阻塞，导致同属KLT的ULT阻塞。使用现代操作系统支持的 `epoll` 系统调用，在内核态创建IO连接的fd，把虚拟线程对象引用关联到fd，然后进入阻塞状态（是自己主动进入阻塞状态，没有进入内核态），负载线程执行其他线程。
另外 JVM 管理专门的 `Read_Poller` 和 `Write_Poller` 线程，死循环执行 `epoll_wait`，负责监控虚拟线程调用非阻塞操作后，在内核注册的fd文件描述符。通过事件驱动，得知fd的状态，或者说非阻塞操作请求的数据是否准备完成，如果准备完成了，通过 fd 关联的虚拟线程对象，把对象状态修改到就绪状态，后续调度到，获取非阻塞操作的结果。

> Java 的虚拟线程机制下， `epoll_wait` 线程的动作是唤醒数据准备好的虚拟线程，不是自己执行处理数据的方法。
> `Redis` 的单线程处理操作缓存的网络连接，死循环运行 `epoll_wait` 的线程在 FD 数据准备好后，直接处理

# 协程

协程和虚拟线程的核心概念相同，解决的问题也是通过非阻塞提交CPU利用率。下面以 `python` 为例子，简单介绍区别。

- 所有标记了 `async` 的方法，在 `python` 看来就是一个协程，是一个堆区中的对象，包含字段
	- 虚拟栈帧（说虚拟，是因为作用和栈帧一样，但是存储内容不一样，不包含完整调用链）：`async` 标记的函数的执行时分配的栈帧，主要内容有局部变量和当前正在执行代码的操作符、操作数
	- PC寄存器的值：标记执行到代码位置
	- 协程对象状态：创建、运行、等待、完成...
	- 上下层对象：一般 `async` 是一个调用链所有的函数都标注，这个字段包含上层协程对象和下层协程对象
	- 异常、返回结果：对应函数正常返回结果和出错时的异常，会通过调用链唤醒上层对象处理


# 精炼描述 虚拟线程和协程

要点：
- 通过非阻塞式的方式，实现事件驱动的多路复用（一个线程监控多个IO系统调用情况，处理其结果）
- 依赖于操作系统提供的 `epoll` 系统调用
差异：
- 虚拟线程是通过将原本一对一的映射方式改为多对多的映射方式，减轻调度压力，再通过将部分IO阻塞操作转为非阻塞操作，借助专门的 `poller` 线程，实现对于非阻塞系统调用的多路复用（`epoll_wait`）
	所以通过非阻塞操作减少内核线程的阻塞引起的调度，以及用户态调度，核心是提高并发线程的执行效率
- 协程本质就是从单线程串行调用IO工作，一步一阻塞，转为通过 `async` 封装成协程，通过主线程的事件驱动循环，执行协程的任务，推进状态变化。
	是在单线程中，能并发执行IO任务，通过协程的状态切换，调度不同的协程执行。
